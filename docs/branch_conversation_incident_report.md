# 分支对话保存失败事故复盘

- 日期：2026-08-03
- 影响模块：会话分支、消息持久化、前端错误展示
- 事故性质：开发阶段功能阻断
- 当前状态：已修复并通过自动化与浏览器验证

## 1. 事故摘要

用户编辑第一条历史消息并创建新分支后，模型能够正常生成回答，但后端在保存回答时触发会话模型校验错误。因此页面表现为回答失败、历史记录空白或“无法连接本地后端”。

第一次修复只允许新分支保存第一轮回答，没有覆盖该分支继续发送第二轮消息的情况。第二轮回答生成后，再次在持久化阶段被拒绝，导致问题重复出现。

这不是 MiniMax、API Key、FastAPI 端口或用户网络的问题。直接证据是后端日志记录了模型厂商返回 HTTP 200，随后才发生本地 `Conversation` 校验错误。

## 2. 用户影响

- 编辑第一条用户消息创建的分支无法稳定继续对话。
- 模型请求已经成功并可能产生调用费用，但回答未能保存和展示。
- 失败后的空分支曾被保留为活动分支，点击历史对话时可能只显示空白页面。
- 后端内部错误响应缺少浏览器需要的 CORS 响应头，前端把服务器错误误判成了“无法连接本地后端”。
- 原有已完成回答没有丢失；失败请求被记录为 `failed Turn`，但当次已经生成的模型回答没有保留下来。

## 3. 真实执行链

| 阶段 | 实际行为 | 结果 |
| --- | --- | --- |
| 1. 编辑首条消息 | 创建一个从会话根位置分叉的新 Branch | 成功 |
| 2. 发送用户消息 | 创建 `pending Turn` | 成功 |
| 3. 构建上下文 | 按新分支历史生成模型输入 | 成功 |
| 4. 调用 MiniMax | 厂商返回 HTTP 200 和有效回答 | 成功 |
| 5. 完成 Turn | 设置回答、完成时间和 Branch HEAD | 内存修改成功 |
| 6. 保存快照 | Pydantic 重新校验完整 Conversation | 校验失败 |
| 7. 失败处理 | pending Turn 被改为 failed Turn | 回答未持久化 |
| 8. 前端处理 | 500 响应因缺少 CORS 头被浏览器拦截 | 被误报为断网 |

2026-08-03 13:29:21 的日志明确记录：MiniMax 请求返回 `HTTP/1.1 200 OK`，模型生成了 111 字回答；紧接着持久化抛出：

```text
Value error, 从根位置分叉的 Branch HEAD 必须从根 Turn 开始
```

因此故障点位于模型回答之后、本地 JSON 写入之前。

## 4. 根本原因

### 4.1 分支领域规则表达错误

编辑第一条消息时，新分支位于原会话第一轮之前，所以创建时具有以下状态：

```text
parent_branch_id = 原分支
forked_from_turn_id = None
head_turn_id = None
```

最初的校验规则错误地认为：只要 `forked_from_turn_id` 是 `None`，这个分支就永远不能拥有 HEAD。这会直接阻止新分支保存第一轮回答。

第一次修复又把规则改成了“HEAD 必须是根 Turn”。该规则只能容纳新分支的第一轮；发送第二轮消息后，HEAD 自然会指向第二个 Turn，而第二个 Turn 必然拥有父 Turn，于是再次被拒绝。

真正需要维护的约束不是“HEAD 是否为根 Turn”，而是：

> 从根位置分叉的 Branch 必须拥有一条独立于父分支的 Turn 历史；HEAD 可以沿这条独立历史持续向后移动。

当前实现会找到新分支 HEAD 所属历史链的根 Turn，并确认这个根 Turn 不属于父分支历史。这样既允许第二、第三轮继续生长，又能阻止新分支错误地引用父分支的 Turn。

### 4.2 第一次修复只修复了症状

第一次修复根据当时的失败状态，把“禁止任何 HEAD”放宽成“只允许根 HEAD”，但没有重新定义完整的分支不变量，也没有把分支继续生长的生命周期纳入验证。

这是问题重复发生的直接原因。修复代码通过了“首轮分支回答”场景，却没有覆盖“首轮分支回答之后继续发送第二轮”的场景。

### 4.3 测试替身没有执行真实持久化

已有 `ConversationService` 单元测试使用记录型 ChatService，只验证创建了新分支以及调用参数正确，没有真正创建 completed Turn，也没有再次运行完整 Conversation 校验。

原有端到端测试覆盖了中间轮次的分叉，但没有覆盖从第一条消息之前分叉并连续发送两轮。因此错误规则在测试中没有被触发。

### 4.4 500 响应位于 CORS 外层

未预期异常原先由 FastAPI/Starlette 最外层错误处理器转换为 500。该响应没有经过 CORS 中间件，浏览器无法读取响应状态与 JSON 内容，`fetch` 只能抛出网络异常。

所以前端虽然具备“服务内部错误”的展示样式，实际收到的却是状态码为 0 的网络错误，最终显示“无法连接本地后端”。

## 5. 已完成修复

### 5.1 修正分支不变量

- 文件：`app/conversations/conversation.py`
- 从根位置分叉的新 Branch 可以拥有任意深度的独立 Turn 链。
- 校验会拒绝新 Branch 混入父 Branch 的历史链。

### 5.2 失败时恢复原活动分支

- 文件：`app/conversations/conversation_service.py`
- 编辑历史消息后，如果新分支生成或保存失败，会自动切回原分支。
- 原有历史不会因为失败的新分支而显示为空白。

### 5.3 保证错误响应经过 CORS

- 文件：`app/main.py`
- 未预期异常现在由 CORS 内层中间件转换为稳定的 JSON 500 响应。
- 前端可以读取 `internal_server_error`，不会再把服务器内部错误误报成断网。

### 5.4 增加回归测试

- 从第一条消息之前创建分支。
- 在新分支保存第一轮回答。
- 在同一新分支继续发送并保存第二轮回答。
- 拒绝新分支错误引用父分支历史。
- 服务器 500 响应必须携带前端来源对应的 CORS 头。
- 完整后端测试共 94 项，全部通过。

### 5.5 恢复当前对话

失败问题“你有没有搜索功能”已重放一次，当前分支包含两轮 completed Turn。浏览器验证已确认第二轮回答和 2.8 秒生成耗时均能正常展示。

## 6. 为什么自动文档返回 200，但聊天仍然失败

FastAPI 自动文档或根健康检查返回 200，只能证明：

- 进程正在监听端口；
- HTTP 路由可以响应；
- 浏览器能够访问基础接口。

它不能证明一次完整聊天事务一定成功。聊天还需要依次完成模型调用、领域校验和本地持久化。本次错误发生在最后的持久化阶段，所以健康检查为 200 与聊天失败并不矛盾。

## 7. 后续防复发措施

| --- | --- | --- |
| 建立分支状态测试矩阵 | 已完成核心场景 | 覆盖根分叉、非根分叉、空分支及连续多轮 |
| 端到端测试使用真实持久化服务 | 已完成 | 模型使用 Fake Client，存储和校验走真实代码 |

| 保存模型成功响应的恢复记录 | 建议后续增加 | 即使最终持久化失败，也应避免丢失已付费生成的回答 |
| 清理历史 failed Turn | 可选 | 当前失败记录不影响展示，可后续提供维护工具 |

## 8. 结论

本次事故由会话分支领域规则设计不完整引起，第一次修复又因为缺少连续多轮测试而只解决了首轮症状。模型厂商、API Key 和网络均不是根因。

修复后的规则围绕“新分支拥有独立历史链”表达，不再依赖 HEAD 是否恰好是根 Turn；同时增加真实持久化端到端测试和 CORS 错误测试，覆盖了本次两次失败所暴露的完整链路。
