# 开发约定：面向契约的可演进架构

本文档约束学习 Agent 的后续开发。目标不是追求抽象数量，而是让每个模块都能被单独理解、验证、替换和重构。

## 1. 总体原则

### 1.1 前后端物理分离

- 后端代码位于 `app/`，只暴露 HTTP 契约，不依赖前端实现。
- 前端代码位于 `frontend/`，只依赖公开 API 和自己的领域契约。
- 前后端不得通过复制内部实现、读取彼此目录或共享运行时对象形成隐式耦合。
- 跨端字段以版本化请求、响应契约为准。

### 1.2 面向契约编程

- 上游只依赖下游暴露的 Protocol、抽象接口、请求模型或响应模型。
- 应用服务负责业务编排，不直接依赖厂商 SDK、文件格式和具体索引实现。
- 基础设施实现可以替换，但不得迫使上游修改业务流程。
- 契约名称描述业务能力，不使用具体厂商或技术名称污染上层。

推荐依赖方向：

```text
HTTP / UI
→ 应用服务
→ 领域模型与能力契约
→ 基础设施适配器
```

### 1.3 按业务板块组织目录

- 不同业务板块使用独立文件夹。
- 文件夹内部再按“契约、模型、服务、适配器、接口”拆分。
- 禁止创建容纳大量无关职责的 `utils.py`、`helpers.py` 或巨型 service 文件。
- 只有被两个以上模块稳定复用的能力，才能进入公共目录。

### 1.4 可观测

一次外部请求至少能够关联：

- `request_id`：HTTP 请求标识；
- `operation_id`：一次业务操作标识；
- `goal_id`：学习目标标识；
- `conversation_id`：会话标识；
- `turn_id`：问答节点标识；
- `provider` 和 `model`：实际模型来源；
- 各阶段耗时、检索命中数、压缩次数和警告。

日志只记录定位问题所需的元数据，不记录 API Key、完整 Prompt、完整用户私密内容和原始检索文档。

### 1.5 可验证

- 每个领域规则必须有单元测试。
- 每个适配器必须有契约测试或可替换的测试替身。
- 每个 HTTP 接口必须有请求、响应和错误测试。
- 修改完成后先运行当前模块测试，再运行全量测试。
- 前端修改至少通过类型检查、单元测试和生产构建。
- 未通过验证的改动不得提交。

## 2. 后端约定

### 2.1 分层职责

- `domain` 或领域模型：表达不变量，不执行网络和文件操作。
- `contracts`：定义上游可依赖的能力，不包含具体实现。
- `application`：编排一次完整用例，处理顺序和失败边界。
- `adapters` 或具体模块：连接模型 SDK、索引、文件和外部服务。
- `api` / `routes`：完成 HTTP 与应用命令之间的转换，不承载业务规则。
- `core/dependencies.py`：只负责组装对象依赖。

### 2.2 数据模型

- 跨边界数据使用 Pydantic 模型，并设置 `extra="forbid"`。
- 领域记录默认采用追加写入；需要移动的只允许是显式书签或 HEAD 指针。
- ID 由调用方预先生成时，服务端必须验证而不是悄悄替换。
- 时间统一保存带时区的 UTC 时间。
- 枚举值进入持久化或 API 后不得随意改名。
- 数据结构变化必须提升 `schema_version` 并提供迁移路径。

### 2.3 异常与错误

- 领域层抛出有语义的业务异常。
- HTTP 状态码与错误码只在统一错误映射层决定。
- 不在路由中捕获宽泛异常并返回模糊字符串。
- 可重试与不可重试错误必须明确区分。
- 降级行为必须通过 `warnings` 暴露，不能静默发生。

### 2.4 外部服务

- 厂商模型、联网搜索、向量模型和索引都通过契约接入。
- 应用层不得导入具体厂商 SDK。
- API Key 只作为当前调用参数向下传递，不放入全局对象。
- 外部调用必须设置超时，并记录不包含秘密的耗时和结果状态。

## 3. 前端约定

### 3.1 状态分层

- IndexedDB 是用户业务数据的唯一持久化真相。
- Zustand 只保存当前界面会话和临时交互状态。
- React 组件不直接操作 IndexedDB，由 Repository 统一读写。
- 服务端 Delta 必须通过一个原子事务应用。
- 临时等待卡片、错误提示和输入草稿不得混入正式 Turn。

### 3.2 组件边界

- 页面组件负责组合，不实现图规则和持久化。
- 地图布局、图规则、API 客户端和数据仓库分别独立。
- 节点组件只接收 Props 和发出事件，不读取全局数据库。
- 组件 Props 使用明确类型，禁止用松散字典传递领域对象。
- 节点坐标和视口属于展示状态，不写入后端领域模型。

### 3.3 用户可理解的失败

- 错误提示说明发生了什么、数据是否保存、用户下一步能做什么。
- 不直接向用户展示堆栈、SDK 错误对象或 HTTP 内部细节。
- 禁止自动执行可能重复计费的 LLM 重试。
- 不支持的模型能力必须在操作前禁用，而不是发送后才失败。

## 4. 变更与提交

每个提交只完成一个可以独立说明和验证的能力：

1. 先确定或扩展契约；
2. 编写领域规则与测试；
3. 接入具体实现；
4. 运行模块测试；
5. 运行全量测试或前端生产构建；
6. 使用中文提交信息提交；
7. 推送到当前 GitHub 分支。

推荐提交前缀：

```text
新增：新增独立能力
修复：修正错误行为
重构：不改变外部行为的结构调整
测试：补充验证
文档：修改说明文档
构建：依赖、脚本或工程配置
```

## 5. 重构判断标准

满足以下条件时，一个模块才算可以安全重构：

- 对外契约清晰且有测试；
- 上游不知道具体实现类型；
- 副作用集中在适配器或仓库；
- 日志能够定位失败阶段；
- 替换实现不要求修改无关模块；
- 旧行为有自动化验证；
- 文件和类的名称能够说明其单一职责。

如果增加抽象不能改善以上任一条件，则暂不增加该抽象。
